# WASEEM MEDICAL PRO — Backend API

واجهة API فعلية مبنية على Laravel 13 وPostgreSQL، مع مصادقة Bearer Token بواسطة Laravel Sanctum، وتقييد الوصول حسب الفرع والدور الوظيفي.

> **الحالة:** اجتازت الهجرات واختبارات API الآلية في GitHub Actions. لم يتم نشر هذه الواجهة على خادم عام بعد، وتطبيق Flutter الحالي ما زال يستخدم التخزين المحلي؛ لا تعتبر بيانات التطبيق متزامنة مع هذا الخادم حتى يتم ربط التطبيق واختباره بعد النشر.

## المتطلبات

- PHP 8.3 أو أحدث ضمن إصدار متوافق مع Laravel 13.
- Composer 2.
- PostgreSQL 16 (موصى به).
- HTTPS في بيئة الإنتاج.

## الإعداد المحلي

من مجلد `backend`:

```bash
cp .env.example .env
composer install
php artisan key:generate
```

عدّل ملف `.env` محلياً لضبط `APP_URL` وبيانات اتصال PostgreSQL. استخدم حساب قاعدة بيانات مخصصاً للتطبيق بصلاحيات محدودة، ولا تستخدم حساب مدير PostgreSQL. لا ترفع ملف `.env` إلى GitHub.

### إنشاء حساب مالك المركز

قبل تشغيل البذرة الأولى، أدخل في بيئة التشغيل (أو ملف `.env` المحلي فقط) القيم التالية:

- `WASEEM_INITIAL_OWNER_NAME`: اسم صاحب الحساب.
- `WASEEM_INITIAL_OWNER_USERNAME`: اسم مستخدم باللغة الإنجليزية، من 3 إلى 100 حرف باستخدام الأحرف الصغيرة والأرقام والنقطة والشرطة والشرطة السفلية.
- `WASEEM_INITIAL_OWNER_PASSWORD`: كلمة مرور قوية لا تقل عن 12 حرفاً.
- `WASEEM_INITIAL_BRANCH_NAME`: اسم الفرع الأول (اختياري؛ الافتراضي «الفرع الرئيسي»).

ثم نفّذ:

```bash
php artisan migrate --force
php artisan db:seed --class=DatabaseSeeder --force
```

بعد إنشاء الحساب، أزل متغيرات كلمة المرور من بيئة النشر ولا تضع كلمة المرور في الأوامر أو السجلات أو Git. لا يوجد حساب افتراضي مثل `admin/1234` في الـ API.

## نقاط النهاية الحالية

كل المسارات التالية — باستثناء `GET /api/health` و`POST /api/auth/login` — تتطلب ترويسة:

```http
Authorization: Bearer <access_token>
Accept: application/json
```

| المسار | الوظيفة |
|---|---|
| `GET /api/health` | فحص توافر الواجهة |
| `POST /api/auth/login` | التحقق من بيانات الدخول وإصدار رمز لمدة 7 أيام |
| `GET /api/auth/me` | بيانات الحساب الحالي |
| `POST /api/auth/logout` | إلغاء رمز الجلسة الحالية |
| `GET /api/patients` | قائمة المرضى مع ترقيم الصفحات والبحث بـ `q` |
| `POST /api/patients` | إنشاء مريض ورقم ملف متسلسل داخل الفرع |
| `GET /api/patients/{id}` | تفاصيل مريض ضمن الفرع |
| `PUT/PATCH /api/patients/{id}` | تحديث ملف المريض |
| `DELETE /api/patients/{id}` | أرشفة المريض بحذف منطقي |
| `GET/POST /api/appointments` | عرض المواعيد وإنشاؤها |
| `GET/PATCH /api/appointments/{id}` | عرض موعد أو تحديث حالته وبياناته |
| `GET/POST /api/packages` | عرض الباقات وإنشاء باقة |
| `GET /api/packages/{id}` | تفاصيل باقة وسجل جلساتها |
| `POST /api/packages/{id}/sessions` | تسجيل جلسة واستهلاك جلسة واحدة عند الحضور |
| `GET/POST /api/invoices` | عرض الفواتير وإنشاؤها |
| `GET /api/invoices/{id}` | تفاصيل الفاتورة ومدفوعاتها |
| `POST /api/invoices/{id}/payments` | تسجيل دفعة وتحديث المتبقي داخل معاملة قاعدة بيانات |
| `GET/POST /api/expenses` | استعراض المصروفات وإضافة مصروف للفرع |
| `GET/POST /api/staff` | استعراض الطاقم وإضافة موظف |
| `GET/PATCH/DELETE /api/staff/{id}` | عرض أو تعديل الموظف أو أرشفته دون حذف سجلاته المالية |
| `GET /api/attendance` | عرض سجلات الحضور مع مرشحات التاريخ والموظف |
| `POST /api/staff/{id}/attendance` | تسجيل أو تحديث حضور الموظف لليوم دون تكرار سجل اليوم |
| `GET /api/payroll` | عرض سجل الرواتب والخصومات مع مرشح الشهر |
| `POST /api/staff/{id}/payroll` | تسجيل صرف راتب أو خصم مع منع تجاوز الراتب الأساسي للشهر |
| `GET /api/reports/dashboard` | مؤشرات المرضى والمواعيد والباقات والفواتير والمصروفات والرواتب |

تُرجع أخطاء التحقق بصيغة JSON ورمز HTTP مناسب. بيانات المرضى والاستعلامات المتعلقة بها محصورة في فرع المستخدم، والعمليات الحساسة تُسجل في `audit_logs`. يتم تقييد المعدل إلى 120 طلب API في الدقيقة، ومحاولات الدخول إلى 5 في الدقيقة لكل اسم مستخدم وعنوان IP.

## الاختبارات

```bash
cp .env.example .env
composer install
php artisan key:generate --force
php artisan migrate --force
php artisan test
```

ينفذ GitHub Actions هذه الخطوات في بيئة اختبار مع PostgreSQL. الاختبارات تغطي تسجيل الدخول، والوصول غير المصرح، وعزل الفروع، وصرف الدفعات ومنع تجاوز الفاتورة، واستهلاك جلسات الباقات.

## متطلبات قبل الإنتاج

1. نشر الواجهة على استضافة يديرها صاحب المشروع مع HTTPS وبيانات أسرار محفوظة في إعدادات الاستضافة.
2. ربط تطبيق Flutter بهذه المسارات باستخدام عنوان API قابل للتهيئة وتخزين آمن لرموز الدخول، وإزالة الدخول التجريبي المحلي.
3. مراجعة الصلاحيات على جميع الأدوار، وإضافة اختبارات جهازية وتكاملية، ومراقبة السجلات وأمان النسخ الاحتياطية.
4. لا تزال واجهات المخزون والموردين والبيع عبر الباركود وقوالب الإشعارات وإرسال الرسائل عبر مزود واتساب للأعمال وSMS غير مكتملة على الخادم.

لا تُرسل بيانات مرضى حقيقية إلى بيئة الاختبار، ولا تعتمد على هذه الشيفرة كنظام طبي إنتاجي قبل النشر الآمن والاختبار التشغيلي.
